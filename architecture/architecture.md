# Architecture — Collections Recovery Analysis

How data moves through this project, from raw export to the numbers in the
dashboard and reports.

```
data/raw/                    17 CSVs, intentionally messy (synthetic dataset, seed=42)
      │
      │  pandas cleaning (dedup, type fixes, timestamp normalization)
      ▼
data/processed/*_clean.csv   one cleaned CSV per raw table, same row-level grain
      │
      │  notebooks/02_load_sqlite.py  (pandas → sqlite, one table per CSV)
      ▼
sql/collections_analysis.db  raw-loaded tables (borrowers, accounts, payments,
                              calls, call_attempts, promises_to_pay,
                              daily_targeting, campaigns, field_visits,
                              complaints, whatsapp_events, sms_events,
                              account_status_history, agent_sessions, agents,
                              vendor_telephony, call_dispositions)
      │
      │  sql/02_data_quality.sql   → profiling: duplicates, nulls, conflicts
      │  sql/03..08_*.sql          → recovery / PTP / targeting / agent / risk analysis
      │  sql/09_account_month.sql  → builds the GOLDEN account_month table:
      │                               dedup'd payments, one row per
      │                               account × month, joined against
      │                               accounts/calls/PTPs/targeting
      ▼
account_month table           the "golden layer" — every dashboard number and
                              every report figure is computed from this table
                              (or from the raw tables directly for data-quality
                              counts, which need to see the messiness itself)
      │
      ├─ sql/10_recovery_metrics.sql   monthly KPIs, MoM %
      ├─ sql/11_claim_test.sql         audits the reported "+11%" claim
      ├─ sql/12_dashboard_data.sql     the JSON blob embedded in the HTML dashboard
      │
      ├──────────────► dashboards/collections_recovery_dashboard.html
      │                 (sql/12 output → embedded JSON → Chart.js, no server needed)
      │
      └──────────────► sql/13_dashboard_workbook.py
                        (pandas queries against account_month/daily_targeting
                         → openpyxl formatting → dashboards/collections_dashboard.xlsx)

reports/*.md                  narrative layer — key_findings.md, executive_memo.md,
                              investment_recommendation.md, metric_dictionary.md.
                              Every number in these is traceable back to the
                              golden layer via metric_dictionary.md.
```

## Design decisions worth knowing

- **Golden layer, not silent fixes.** Duplicates are removed (`payments`
  deduped on `payment_id`), but ambiguous problems — `outstanding_amount >
  principal_amount`, payment/account borrower conflicts, agent identity
  conflicts — are **flagged and excluded from the affected cut**, not
  guessed at. See `reports/metric_dictionary.md` → "Golden dataset
  construction rules."
- **One source of truth for definitions.** `reports/metric_dictionary.md` is
  authoritative. If a number in an older `sql/*.sql` script disagrees with
  the dictionary, the script hasn't been reconciled yet — trust the
  dictionary and the `account_month` table.
- **`account_month` denominator is a snapshot, not a monthly history.**
  `accounts.outstanding_amount` is a current snapshot, so "recovery rate" is
  computed against one fixed portfolio-outstanding figure across all months.
  This is deliberate (isolates recovery changes from portfolio-size changes)
  and documented, not an oversight.
- **`sql/01_schema.sql` is a placeholder.** The database was built directly
  from `notebooks/02_load_sqlite.py` (pandas `to_sql`, inferred types)
  rather than a hand-written `CREATE TABLE` schema. If you need explicit
  column types/constraints, generate them from `PRAGMA table_info(...)`
  against `collections_analysis.db` — don't assume `01_schema.sql`
  reflects the live schema.
- **Two dashboards, same numbers, different jobs.** The HTML dashboard
  (`dashboards/collections_recovery_dashboard.html`) is the primary,
  interactive artifact — open it in a browser, no dependencies. The Excel
  workbook (`dashboards/collections_dashboard.xlsx`) is a static export of
  the same golden-layer numbers for people who live in spreadsheets or need
  to pull the figures into another model. Both are generated by scripts
  (`sql/12_dashboard_data.sql` and `sql/13_dashboard_workbook.py`
  respectively) so they can be regenerated after any upstream change.

## Reproducing the pipeline end to end

```bash
# 1. Clean raw → processed (see notebooks/01_data_profiling.ipynb for the
#    profiling that drove each cleaning decision)
jupyter nbconvert --to notebook --execute notebooks/01_data_profiling.ipynb

# 2. Load cleaned CSVs into SQLite
python notebooks/02_load_sqlite.py

# 3. Run the SQL pipeline in order (01 is a placeholder, start at 02)
#    02 → data quality profiling
#    03-08 → recovery / PTP / targeting / agent / risk analysis
#    09 → builds account_month (the golden layer)
#    10-12 → recovery metrics, claim test, dashboard JSON
#    (run each .sql file against sql/collections_analysis.db with your
#    SQLite client of choice — these are analysis queries, not migrations,
#    so there's no single runner script; account_month (09) is the one that
#    actually mutates the database)

# 4. Rebuild the Excel workbook from the golden layer
cd sql && python3 13_dashboard_workbook.py
```
